## Intent

Networks whose users live in an external identity provider (OneLogin, Okta, any SAML 2.0 IdP) need a way in that does not create local WordPress passwords. The login screen should offer an "Sign in with OneLogin" button; a user with an active IdP session clicks through with no prompt (SAML's natural behavior). With mapped domains and multiple sites, that external login must still land the user on the site they wanted — not just the network's main site.

## Acceptance criteria

- When a network configures a SAML IdP, every site's login screen shows an external SSO button (configurable label, default "Sign in with OneLogin") next to the network SSO button.
- Clicking it from a client site carries the destination through: OneLogin → identity site ACS → PV WPMS ticket → logged into the originating site, no second prompt anywhere for a user with a live OneLogin session.
- Clicking it on the identity site itself logs the user into the identity site directly.
- A SAML Response is accepted only when: the assertion signature validates against the configured IdP certificate, the audience is this SP, the destination is the ACS URL, timestamps are within the allowed window, and `InResponseTo` matches a request we issued (replay closure).
- An assertion whose email matches no WordPress user is refused with a readable notice — unless the network enabled auto-provisioning, in which case the user is created (email verified by the IdP) with the configured default role.
- `GET /wp-json/pv-wpms-sso/v1/saml/metadata` returns valid SP metadata XML (entity ID, ACS redirect/consumer endpoints, email NameIDFormat) for pasting into the IdP.
- SAML users pass the same destination-network scope at ticket mint/redemption as network users (super-admin default blocks them unless widened — consistent, documented).
- All SAML features no-op cleanly (with an admin notice) when the bundled library is absent; network SSO keeps working.

## Non-goals

- IdP-initiated flow (unsolicited responses) — SP-initiated only.
- SLO / single logout; logout propagation stays out of scope.
- Multiple IdPs per network (decision: revisit clause).
- OIDC / OAuth providers.
- Signing the AuthnRequest with an SP keypair (SP signing off; IdP-signed assertions required).
- Per-site SP topology (rejected — one ACS URL per mapped domain in OneLogin is unmanageable).

## Design

Hub-and-spoke (decision 0005): the identity site is the only SAML SP. The client-site button does exactly what the network-SSO button does — creates a state — then hands off to the identity site's SAML start, carrying `client_blog_id` + `state` in `RelayState`. After ACS validation and user mapping, the existing ticket mint (extracted from `AuthorizeEndpoint` into a shared `TicketIssuer`) runs with those parameters. On the identity site itself, the button skips RelayState and logs in locally.

Components:

- `SamlSettings` — per-network option `pv_wpms_sso_saml`: enabled, idp_entity_id, idp_sso_url, idp_x509cert, button_label, auto_provision, default_role.
- `TicketIssuer` — extracted from `AuthorizeEndpoint`: mint ticket for (user, client blog, state) and produce the callback redirect. Shared by authorize and ACS.
- `SamlProvider` (identity site): builds php-saml SP settings; `start()` creates the AuthnRequest (stored request ID transient) and redirects to the IdP; `consumeAcs()` validates the POSTed response, maps the user, sets IdP cookies, and branches (ticket redirect vs local admin).
- `SamlFlow` — `login_init` handler: `pv_wpms_sso=saml_start` on any site; `action=pv_wpms_sso_saml_acs` (POST target) on the identity site.
- `SamlMetadata` — REST GET returning SP metadata XML.
- `UserMapping` — email → existing user; provisioning (username from email local part, deduped) when enabled.
- `LoginScreen` — renders the external SSO button alongside the network SSO button.
- Settings page section: External SSO (SAML) fields + the SP metadata/ACS URLs shown for copy-paste.
- WP-CLI `status` gains a SAML line.

Library (decision 0006): `onelogin/php-saml ^4.0` (MIT) as a composer runtime dependency; the CI build job vendors it into the `-built` branch; the plugin requires `vendor/autoload.php` when present and gates all SAML wiring on class presence.

Runner-up: hand-rolled SP. Rejected — XML-DSig validation is the security-critical core and a proven library beats an in-house verifier. Runner-up: per-site SPs. Rejected — an app per mapped domain per network in OneLogin.

Testing: unit tests for settings merge and user mapping/provisioning decisions (pure parts); integration tests under wp-env for start redirect shape (deflated `SAMLRequest` decodes to a valid AuthnRequest), metadata XML, ACS rejection paths (bad signature, wrong audience, unknown `InResponseTo`, no user), and one full crypto round trip (response signed with a generated keypair via `OneLogin\Saml2\Utils::addSign`, consumed by the ACS, ticket minted to the client site).

## Rulings

- [signature-mode] `wantMessagesSigned` (response-signed, OneLogin/Okta default) rather than assertion-only signing — `Utils::addSign` test path and IdP dashboards both favor it; assertion-only configs are rejected and documented — cost if wrong: medium, assertion-only IdPs (some Azure AD configs) need a setting later.
- [settings-api] `Settings::save`/`SamlSettings::save` merge over stored values, not defaults — partial updates were silently wiping configuration; caught by the SAML integration suite — cost if wrong: high (unconfigures live networks).
- [relay-state] RelayState mirrors client params for the IdP's benefit only; redemption trusts the stored request transient, never the echoed RelayState — cost if wrong: high.
- [error-surface] ACS failures return opaque `saml_invalid_response` to users; the reason goes to `pv_wpms_sso/saml_validation_failed` for admins — cost if wrong: medium (leak vs debuggability).
- [admin-ux] The SAML settings section edits the identity site's own network (cross-network setups show a notice and require super admin) — the SP is the identity site, so its network is where the app config belongs — cost if wrong: low.

## Deferred

- Multiple IdPs per network (settings schema is per-network single; a future `providers` array is a schema change with a migration).
- IdP-initiated (unsolicited) responses — weaker binding, rarely needed with OneLogin bookmarks.
- SP-initiated signed AuthnRequests (needs SP keypair management; OneLogin works fine unsigned).
